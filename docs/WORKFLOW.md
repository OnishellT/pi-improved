# Workflow

One idea: **the cheap model implements, code decides when work advances, and the strong model and the person step in only where they add value.** Below is the expected flow from first session to deploy, and what the package covers today.

Everything is **language- and framework-agnostic**. No stack-specific gates ship in the package. Verification commands come from the project (`.pi/workflow.json`; every key is in the [README table](../README.md#config)). Code checks read plain text (names, files, diffs) and never parse a language.

## Flow at a glance

| # | Stage | Who | Tools | Status |
|---|-------|-----|-------|--------|
| 1 | Initial setup: docs, skills, rules | `setup` model + person | `/setup`, setup skills, agentlint | Covered |
| 2 | Planning | `implement` model, `review` model check | `/task`, `task_plan`, verified names, plan check | Covered |
| 3 | Implementation with specific context | `implement` model | Recorded plan, `tdd` skill, automatic pauses | Covered (isolated subagent: see Pending) |
| 4 | Real verification in the expected environment | Code (`verify`) | `verify-app` (browser, CLI, API or TUI), compiler, linter, tests | Covered |
| 5 | agentlint | Code (`verify`) | Rules in `.agentlint/config.ts` | Covered |
| 6 | Error correction | Orchestrator. 2nd failure: diagnose; 3rd: `escalate` model; then the person decides | `verify` gate, `diagnosing-bugs` skill, diff review | Covered |
| 7 | PR with static checks | Orchestrator | `/pr`, `gh`, the repo's PR template | Covered |
| 8 | PR review in CI | Project CI | Linters, tests, agentlint | Out of package |
| 9 | Deploy | Project CI/CD | Project pipeline | Out of package |
| 10 | Manual verification | Person | Deployed environment | Out of package |

**Covered**: package code runs it and blocks on failure. **Pending**: next piece to build. **Out of package**: project and person work that pi-improved prepares but does not run.

## 1. Initial setup

Once per repo, with the strongest model available (`models.setup`). Its output is the context cheap models read later, so spend here.

`/setup` does:

1. **Scan (code, no model):** stack, package manager, CI, docs, candidate verify commands, and connectors (Jira, Linear) from the git remote, ticket keys in commits and URLs in docs. Then ask the minimum: language (skipped when set in either config file), one read-only question per connector, and agentlint for Node projects. A connector or agentlint you said no to is stored and not asked again. Esc at any of these questions stops setup before the model run.
2. **Interview:** the model follows the `grilling` skill. One round at a time, each one `ask_user` call (at most 5 questions), recommended option first, nothing the code answers. About 12 questions at most (`limits.interviewQuestions`).
3. **Documents:** `GLOSSARY.md`. `AGENTS.md` (max 150 lines: purpose, stack, commands, map, conventions, MUST/NEVER rules). `docs/adr/` for decisions the code shows or the person confirmed. `.pi/skills/domain-<area>/SKILL.md` per business area.
4. **App verification skill:** following `pstack-create-verification-skill`, write `.pi/skills/verify-app/SKILL.md` with an executable script when the app can run without a person (a features map under `.pi/skills/verify-app/features/`, one file per feature, plus `features/coverage.json` with `sync` (the output of `git rev-parse HEAD`) and `paths` (the code the map covers)): headless browser (web), the binary (CLI), calls (API), the terminal (TUI). Evidence goes to `.pi/evidence/`. Stage 4 uses it to test real behavior, not only unit tests. If a GUI-driving CLI is available (`pi-desktop` on PATH, or the desktop turned on with `/computer`; see [COMPUTER.md](COMPUTER.md)), the scan reports it and the script may use it for what a headless run cannot reach. Only command line tools qualify: `verify` trusts exit codes, so MCP-only drivers cannot gate.
5. **Rules (Node projects only):** if the person accepts (or `useAgentlint` is `always`; `never` skips this step), install agentlint and turn up to 3 (`limits.agentlintRules`) `AGENTS.md` MUST/NEVER rules the person picks into agentlint rules: those a pattern can detect but a person must judge. Human authority by default. Adopt gradually. Never accept findings in bulk. If the person turns agentlint down later, `setup_finish` offers to drop it instead of refusing for a missing config.
6. **`verify`:** leave the project's verify commands ordered fastest first (compiler or typechecker, linter, tests, `verify-app`, agentlint), then call `setup_finish`. It checks in code that files exist and are well formed (for the verify-app skill: a script, a features map whose files have their headings, and a required `coverage.json` whose `sync` resolves to a commit (`git cat-file -e <sync>^{commit}`) and whose `paths` all exist), runs `verify`, and asks for one approval. `.gitignore` gets `node_modules/` and the local state paths before the dialog lists the files; the list shows the first 40 and counts the rest. A check that fails here only because a service it needs is missing stays out of the list; `AGENTS.md` "Before finishing" and the setup summary name it and the service, so a later session or another machine can run it. The list may be empty when no check can run here (the approval says so, and the gate then never closes a task on its own). After 3 failed runs the person may finish with verify pending; without a UI setup finishes that way instead of pausing, and without the approval nobody could give (the files stay uncommitted).

If the model stops early, a hook pushes it on (max 2 times per message). If `verify` fails 3 times, the person decides.

Result: `.pi/workflow.json` with `setup: "done"`, `language`, `startedAt`, `completedAt`, `verify`, `connectors`, and `agentlint` and `agentlintStep` if used, plus what you declined (`declinedConnectors`, `agentlintDeclined`). Setup picks no models: that is `/models`. Versioned.

After setup, pi reloads and a `[setup]` message in the chat gives the next step: `/models` when no review model is set (without one, no review runs), then `/task`. When `models.setup` is not set, `/setup` first says which model it runs on; press Esc, run `/models`, then `/setup` again for a stronger one. The startup offer of `/setup` comes back on the next launch after Later or Esc. "Don't ask again" is kept for you only (see Internals, State).

## 2. Planning

`/task <description | PAY-142 | path/to/spec.md>` starts a task. The orchestrator (`implement` model) reads the ticket via MCP, named spec files, `GLOSSARY.md`, `AGENTS.md`, related skills and ADRs, similar past tasks from `.pi/memory/tasks.jsonl`, and the code it will touch plus its sibling files. It edits nothing: write and edit calls are blocked until the plan is recorded.

`/task` alone shows the task and what to do next. `/task continue` resumes planning a task still in `planning`. `/task done` closes an implementing task, and `/task cancel` drops any task. Running `/task <new text>` while a task is open asks whether to replace it; a planning task also offers "Continue it", and "Keep it" changes nothing. With a ticket key and no tracker enabled, a warning says the agent sees only the key, and how to paste the ticket text. A session that starts with an open task says so, with the same next steps.

With `understanding` set to `plan+end` (the default), the user reasons first: before proposing a design, the agent asks how they would approach the one or two most consequential decisions, in one `ask_user` call with open questions and no recommendation. The plan builds on their answer, and where it is wrong or risky the agent says why, with evidence from the code. "skip", or a request for a proposal, gets a proposal. Open answers are not recorded as decisions. Without a UI the agent plans straight away. Nobody can answer a question then, so pi takes the recommended (first) option of each open decision and accepts the proposed interface names. It records each choice as "chosen without the user" in the plan and in the ADR, and says so in a notice. The task never stays in `planning` waiting for an answer.

It then calls `task_plan` with:

- `intent`: the ticket restated in the plan's own words, one short paragraph. Required. The plan check and the review compare against it, the `/pr` Summary shows it, and it goes into the memory record.
- `summary`, `steps`, `files`.
- `decisions`: only choices no document settles, 2 to 4 options each. Choices the code cannot resolve go to the person and are stored as ADRs in `docs/adr/`. pi writes them once the plan is recorded, not the model, and tells the model their paths so it keeps them in the change. What the person already answered through `ask_user` while planning is added as a decided choice too, with its ADR, and is not asked again. A run with no UI takes the first option (see above).
- `interface`: file, exports and signatures the tests will import, citing the source (ticket, doc or existing file), and, for callables, an optional `usage`: the call a test would make, in the ticket's words (e.g. `slugify("Hello World")`). `usage` is plan text, not a gate: the plan check reads it, and the review brief lists it.
- `seams`: test points per the `tdd` skill. Each ticket acceptance criterion, invalid-input ones included, needs one.

Two checks run before the plan is recorded:

- **Verified names** (`src/contract.ts`). Each `interface` name must appear as a word in its cited source (ticket text read via MCP, spec files named in `/task`, docs, or existing code) or in the ticket itself (title, request text, tracker text, spec files). Plurals and simple inflections count: `users` gives `user`, `listing` gives `list`. A new file needs every word of its name there. Only names found nowhere are asked, in one dialog: "The ticket does not name these. Use them?". The accepted names stay in `.pi/task.json` as the plan's "Interface names" decision, and `/pr` lists them. pi writes no ADR for them. Plain text, any language.
- **Plan check** (`src/plan-check.ts`). A read-only child with the `review` (or `setup`) model reads the ticket, interface and sibling files. It returns `VERDICT: OK` or a fix list: names that break the folder convention, argument shapes that differ from the ticket's, existing helpers being duplicated, invalid inputs left uncovered, files missing from or wrongly in scope, and an intent that does not restate the ticket. Once per task (`limits.planChecks`; `0` turns it off). Off unless `review.plan`, `review.always` or a `review.minLevel` other than `off` (default `high`, see the README table) asks for it; the policy applies only when the plan touches high-risk files. On fixes, the orchestrator corrects the plan and calls `task_plan` again. A plan check that is not wanted, could not run, or gave no verdict is recorded as `plan-skipped`: /metrics counts it in its `Plan checks` line, never as a code review. One that never started costs nothing; one that ran without a verdict keeps its cost in the task total.

**No plan approval.** The person confirms at the end, not at the plan: the questions above (the approach, open decisions, invented names) are the only dialogs while planning. Pressing Esc on one pauses planning: a notice says `Planning paused at: <question>. /task continue resumes planning, /task cancel drops it.`, and no reminder sends the agent back to `task_plan` until you write again. `/task continue` (or a reply in the chat) asks only the questions that are still open. Backing out of the "Other answer…" text box shows that question's options again. Answers are kept for the current session only: after a restart, `/task continue` asks them again. Once the gates pass, pi writes the ADRs for the answered decisions (not for interface names), `.pi/task.json` keeps the plan and becomes `implementing`, and one notice says so, e.g. `Plan recorded: 4 steps, 6 files. Implementing.`, with the risk reasons when there are any: over 8 files, 6 interface entries or 2 decisions (`limits.fastPath.files`, `.interface`, `.decisions`), or a risk trigger (dependency files, migrations, sensitive areas, `review.paths`, `review.always`; `planRiskReasons` in `src/risk.ts`). The plan itself is never printed in a dialog. With no UI (`pi -p "/task ..."`), pi takes the recommended (first) option of every closed question, in `task_plan` decisions and in the planner's `ask_user` calls, and the decision and its ADR say `chosen without the user`. A headless `/task` plans, implements and runs verify in one command.

**No baseline.** Recording a plan runs no verify: implementing starts at once, and verify runs only at the end. A failure in code the change did not touch may be old, so the gate's advice tells the agent not to fix it outside the plan and to report it to the user at the end. If the new tests, or a service they need, cannot run here, the agent keeps implementing; verify reports what did not run.

**AGENTS.md sections.** `/setup` has the model add two short `AGENTS.md` sections: "Before finishing" (the `verify` commands) and "When to use /task" (dependencies, migrations, `review.paths`, big changes). Without an active task only the verify gate runs, after a turn that changed files; the contract check, the review and the "is the task done?" question need a task in `implementing`. Older setups wrote a `mode` key; it is ignored.

## 3. Implementation with specific context

Target: **an agent that receives only what it needs** implements. Its input is the recorded plan, interface, seams, relevant ADRs and phase skills. No planning conversation, no other tasks. The less context a cheap model carries, the better it follows the plan.

Code pauses and asks when the agent (while the task is `implementing`):

- touches files outside the plan's `files`;
- adds dependencies, by command or by editing `package.json`, `pyproject.toml`, `go.mod`, etc.;
- creates migrations or changes schemas.

Without a UI (print mode) nobody can answer, so the scope and migration pauses are off, and a new dependency, or a manifest edit that cannot be checked, is denied with a reason to the agent.

If the agent ends a turn on a plain-text question, the TUI leaves it for you to answer. While implementing in RPC or print mode, a nudge sends it to `ask_user`. While planning, the reminder says "Call task_plan with your plan. For a real open question, call ask_user first." `ask_user` without a UI tells the agent to make the choice that fits `AGENTS.md` and the ADRs, and to name it in its final summary; during `/setup`, to list it as an open question in the docs.

When `limits.verifyEvery` is set (default 0: off), every that many writes code runs the first `verify` command and appends the result to the write or edit result as a "Progress check". It is a hint, not the gate: nothing is blocked and no retry is counted. It has a 60 s cap, and times itself: when a run takes 30 s or more, or times out, progress checks are off for the rest of the task, and that write result says why, once. A failure can be expected mid-change (a test for code not written yet), so the result tells the agent to fix it only if it is not.

## 4. Real verification

When the agent calls the task done, code does not believe it. In `agent_before_settle`:

1. **Interface contract.** Each plan export must appear in its file. If one is missing, the task returns to the agent without spending verify time or review money.
2. **`verify`.** Commands from `.pi/workflow.json` run in order: fast ones first (compiler, typechecker, linter), then tests, then `verify-app`. `verify-app` exercises the functionality in the real environment with the tools setup left: open the screen in the headless browser, run the CLI command, call the endpoint, walk the TUI. Evidence goes to `.pi/evidence/`.

The agent cannot close the task while `verify` is red. It gets 3 automatic retries (`limits.verifyRetries`). The 1st failure asks for a fix. The 2nd asks the current model to diagnose the bug (reproduce, isolate, hypothesis, then fix). At the `limits.failuresBeforeEscalation`-th failure (default 3) the `escalate` model takes the attempt, even when the retries are used up. With the limit at 2 or lower, the diagnosis and the escalation come together. After that the person decides. Interface-contract misses have their own retries, the same number. The first failing step stops the run. The agentlint step is the one setup recorded (`agentlintStep`, always a step of its own) or a bare `agentlint check …`; a script or compound command that also runs agentlint is an ordinary step, and the words in the output do not matter. The recorded step runs first. A setup from before the record gets the standard step added and recorded the first time its manifest is read. The gate treats a new commit like any other change, so work made and committed through bash is verified too. If Nix is missing or cannot build its package (offline, disk full), verify did not run: one notice, no dialog, says "Verify did not run" with Nix's message, and that the task stays open (once this is fixed, `/verify` checks the change and `/task done` closes the task). No retry, escalation or model turn is spent. `/verify` runs it by hand and shows a status while it runs. Commands come from the project, so the same flow serves TypeScript, Python, Go or anything else.

## Optional: Bend laws

For a rule that must never break (pricing, permissions, a state machine), a project can keep `LAWS.bend`, written by a human, at its root. [Bend](https://bend-lang.com) is a language where the agent can prove such laws in `PROOF.bend`; it proves Bend code only. For any other language the agent writes a small Bend model of the rule, proves the laws on it, and adds a test to the project's own suite that compares the real code with the model (through `bend Model.bend <args>` or a compiled binary).

- `/setup` can also create laws: when the interview finds pure-logic invariants and the project has no `LAWS.bend`, it offers to record them (`useBend` in `.pi/workflow.json`: `ask` by default, `always` skips the question, `never` leaves Bend out). Each law is shown in plain words and written only if approved, with a minimal Bend model.
- Setup proposes `BEND_NO_TELEMETRY=1 bend --check-only PROOF.bend` as a verify step when `bend` is on PATH and `PROOF.bend` exists, and adds it to an existing `verify` when `/setup` runs again. If `bend` is missing it says how to install it (`curl -fsSL https://bend-lang.com/install.sh | sh`, no sudo, into `~/.bend`) and never installs it.
- In a `/task`, editing an existing `LAWS.bend` is one of the quality gates (below): high risk, and listed in the completion dialog whatever the review policy; edits to a `LAWS.bend` that was uncommitted when the task started are not flagged. `PROOF.bend` is a verify file like any other: an edit the plan does not name is flagged too.
- An on-request `bend-laws` skill is listed in plan and implement, and the implement prompt and the main session's prompt gain one rule, whatever implement skills the project picked: critical logic is verified against the laws, and `LAWS.bend` is never edited without the user's approval; `/doctor` shows the `bend` version.
- Without a `LAWS.bend` none of this exists outside `/setup`: no prompt text, no skill, no check; `useBend: never` removes the setup offer too. Bend sends a daily version ping unless `BEND_NO_TELEMETRY=1`, which the verify step sets.

## 5. agentlint

`agentlint check --all` is one more `verify` step. It checks the MUST/NEVER rules setup turned into code. If a rule fails:

- the agent gets one attempt to fix the code;
- if the agent thinks the code is right, it records its reason with `agentlint propose`;
- if it fails again, the person decides: fix, or accept. pi shows each finding (rule, file, line, the agent's note) and asks for its own reason; an empty reason sends the rest back to the agent. Each acceptance is recorded with `agentlint approve` and a human actor, because pi has no TTY and may run inside another agent.

agentlint has no warning mode: a configured rule always blocks. So setup picks the lifecycle by what the rule judges: `change` for rules about changes (only the diff against the merge base is judged, existing code is never flagged), `state` for rules about the current code. Findings a `state` rule has in existing code are narrowed by the agent or shown to the person by `setup_finish`, one by one, the same way.

Guards: an agentlint exception always needs the person, even when the rule lets the agent decide. After every bash command and before the gate verifies, lines in `.agentlint/acceptances.jsonl` the person has not seen are shown for approval: "Keep these agentlint exceptions? (No: they are removed)", one line each, `- <rule> (<detector> #<fingerprint>): "<reason>" (by <actor>)`, plus `; last check: <rule> at <file:line>` when agentlint's last check has the same finding (only a hint: that cache is model-writable). Declined, or with no one to ask, the file is restored. The model cannot write or edit that file. Commands that open the interactive UI (`review`, `--review`, `--wizard`) are blocked, because they would wait for someone.

## 6. Error correction

The `verify` report returns to the orchestrator with instructions. Pressure rises with each failure:

| Failure | What happens |
|---------|--------------|
| 1st | "Fix it and finish." The gate message starts with "Verify failed (1 of 3): retrying." (the count is `limits.verifyRetries`). |
| 2nd | `diagnosing-bugs` skill injected: reproduce, isolate, hypothesize, then touch code. Same model. It starts with "Verify failed (2 of 3): diagnosing, then retrying." |
| 3rd (`limits.failuresBeforeEscalation`) | Switch to the `escalate` model (or `review`, or `setup`) for that attempt, even past the retries. A notice says `Verify failed 3 times: <model> takes this attempt, then you decide.` With retries left after it, "takes this attempt and N more"; headless, "then the run stops". That gate message has no "(n of m)" line. At 2 or lower it comes with the diagnosis. |
| After the retries | The person decides (see below). |

When the gate stops, it says so once:

- **Verify still fails after the retries.** With a UI, the end of the last report is shown (not when the last gate message already shows the same failure), then "Verify failed N times, last with <model>. What now?" (Keep trying / Leave it as is). N counts every failed verify since the last pass or user turn, agentlint failures included. "Leave it as is" says the task stays open: after your fix, `/verify` checks it and `/task done` closes it. Headless (`pi -p`), print mode drops notices, so the gate writes one line to stderr, `[pi-improved] Verify failed N times, last with <model>. The task stays open: /task done closes it.`, and sets exit code 1; a later prompt of the same run that passes verify gives the exit code back. A missing plan interface gets the same treatment ("The plan's interface is still missing after the automatic retries.") with what is missing, and headless its own stderr line.
- **Verify could not run.** One notice, as above.
- A turn that changes nothing does not run the gate again: `/verify` and `/task done` are the way on.
- A TUI turn that ends on a question waits for your reply: "The agent asked a question: verify runs after your reply."

When the same failure comes back (the last two signatures are equal: same failing step and the same output lines the same number of times, times, durations and hex addresses normalized and whitespace collapsed; paths stay), the report from the diagnosing failure on (the 2nd, or the 1st when `failuresBeforeEscalation` is 1), also carries three premise lines: state the false assumption behind the earlier fixes, name an observation that would contradict it and check it before touching code, and start again from what was observed if it was wrong.

Risk is measured on every pass against the task's `baseCommit` (HEAD when it entered implementing, so commits the agent made still count): `git diff <base>` plus untracked files, read without following a link or waiting on a FIFO (a new binary adds no lines, a link or FIFO one, a text file over 1 MiB its size at 40 bytes a line). Without one it uses the last commit before the task started, and with neither there is no base: the whole tree counts as changed, every test and verify file is touched, and risk is high (`no base`). Never `HEAD`, which would hide commits made during the task. The level is `none`, `low` (over 200 lines or 6 files, no plan, new user decisions; a test file is one in a `test`, `tests`, `__tests__`, `spec`, `e2e` or `__mocks__` directory, or whose name has `test`, `tests` or `spec` as a separated word or CamelCase suffix, such as `a.test.ts`, `a_test.go`, `test_a.py`, `ATest.java`) or `high` (over 600 lines or 15 files, dependencies, migrations, `review.paths`, sensitive zones, or a change to a file that existed before the task and looks like a test or is named by a `verify` command, such as a script path, or `package.json` when a command runs a package-manager script, unless the plan lists it in `files` or a seam: the model may have edited the test or the setup to turn verify green); The `review.*` thresholds tune it. Level and reasons appear in the gate's final summary, and the completion dialog lists those test and verify files before the person accepts. The implement prompt tells the model not to change them unless the ticket asks. A model review is requested when `review.always` is set (it beats `review.never`) or the level reaches `review.minLevel` (default `high`; `off` never reviews), and needs `models.review`; without it the gate warns once per session ("This change needs a review, but no review model is set. Run /models and pick Review.") and runs none. When the policy is `off` (or `review.never`), the review is recorded as `not-requested`, shown as `n/a` in `/metrics` and not counted as skipped for low risk; `skipped-low-risk` is only a diff below an active policy, for a task no review ran on. When requested, a read-only child with the `review` model reviews the diff against the plan, ADRs and `AGENTS.md`, following `pstack-blast-radius`. One round, and never twice for the same diff. If it asks for changes, the cheap model makes them and `verify` checks them, not another paid review. Below the configured level, no review is paid. Without tmux, or on failure, the review is skipped and the person is told.

**Risk line.** The gate says the risk and the review once, at the end: `Risk <level>: <reasons>.` followed by one of `Review: approved.`, `Review: changes requested; the agent fixes them.`, `Review did not run: <why>`, `Review: not needed at this risk.`, `Review: off (review.minLevel).` (or `review.never`), `Review: not run, no review model is set.`, `Review: already ran on this diff.` or `Review: not run on this diff (one review round per turn).` It is in the done dialog when there is one, otherwise a notice. Nothing is said when the risk is none with no reasons and no review ran, and nothing before verify or on retries.

**Quality gates.** The risk assessment also raises a change to high risk, and lists it in the completion dialog, when: a task that reads as a bug fix (title, body or plan intent) changes source but no test; a test diff removes or edits assertion lines or adds skip/only/xfail/retry markers; or the diff passes `limits.changeCap` lines. These are path and line checks, not language rules. The reviewer's brief also carries the verify commands (it cannot run them; the gate does, in parallel) and fuzzy warnings from scanning added lines for swallowed errors and commented-out code.  `/pr` runs verify before it offers to commit, stops without committing when verify fails (with no verify steps configured, nothing runs before the commit), and keeps the commit subject within 72 characters.

The done dialog, after verify and after the review when one runs, lists every file the task changed since its `baseCommit`: tracked changes and new untracked files, outside `.pi/`, one sorted line each with its status (added, modified, deleted) and +/- lines, up to 30 and then "…and N more". Ignored files are left out, as in a commit; a binary file says so, and a new text file over 1 MiB or a symlink shows no counts. When git cannot list the files, the dialog says so. When the person confirms the task is done (without a UI, a passing verify is the answer; and with no verify steps the task stays open and a notice says why; with a UI the person's answer closes it either way), a record goes to `.pi/memory/tasks.jsonl` (versioned) and a notice says `Task done: <title>.`, as `/task done` does. The record feeds the planning of future tasks (stage 2). If it cannot be written, a warning says so: future plans will not see that task. Declined, or left unverified, the task stays open: `/task done` closes it later, `/task cancel` drops it, and both switch back to the model in use before `/task`. A session that starts with a task still open says so once. Every 5 finished tasks (`limits.retroEvery`; `0` turns the reminder off), a notice says how many tasks are finished and suggests `/retro`. The retro never starts on its own. `/retro` reviews the last `retroEvery` tasks (5 when the reminder is off); `/retro 3` reviews the last 3. Run during a turn, it starts when the current run ends. It uses the `retro` skill and proposes edits to `AGENTS.md`, ADRs or skills through questions, and writes nothing without your yes. When the code the verify-app skill covers (`features/coverage.json`) changed since its `sync` commit, the retro prompt also points to `pstack-maintain-verification-skill` (on demand), which ends by setting `sync` to the output of `git rev-parse HEAD`. If the `sync` commit no longer exists, the retro says so and asks to refresh the coverage.

**Understanding check.** Unless `understanding` is `off`, a task the person confirmed done is not closed yet: the gate sends the agent to the `understanding-check` skill. In one `ask_user` call it asks 2-3 open questions drawn from the diff (behavior, failure modes, why the change fits the agreed decisions), answers each reply in a line or two (confirming, or correcting with `file:line`), and calls `understanding_done`, which records the outcome and completes the task. A requested review that asks for changes comes first, so the check sees the final code. Code changed during the check, by the agent or between turns, goes through verify and the done dialog again before `understanding_done` can close the task. The person can answer "skip", or close the task with `/task done`; either is recorded as skipped, never asked again. Without a UI there is no check (`no-ui`). It never blocks implementing or `/task done`, and small edits outside `/task` get none. `/metrics` shows the outcome rates and the gaps per answered check; the gaps themselves stay out of the PR.

## 7. PR with static checks

`/pr [base]` prepares the branch and the PR with `gh` and the repo's PR template. The body, after the template when there is one, has these sections: Summary (the plan's intent, summary and steps), How it was verified (the `verify` report, agentlint included), Risk, New ADRs, Decisions (one line per settled planning decision, question → answer, including interface names accepted while planning and options pi picked without a UI; left out when there are none) and Tests (the plan's seams). `/task` does not commit, so when work is uncommitted `/pr` offers to commit it with the task title as the message. The commit includes the versioned `.pi/` state (`workflow.json`, `memory/tasks.jsonl`, `skills/`) and leaves out only what stays on this machine: `task.json`, `metrics/`, `evidence/` and a legacy `contract.json`, the same list `/setup` puts in `.gitignore` (`LOCAL_STATE` in `src/task-state.ts`). Files in `.pi/evidence/` at the repository root (screenshots, logs from the verify-app skill) are listed in the preview, not in the body: attach what reviewers need. If the branch already commits evidence files, the preview warns that they will be pushed. A status shows while verify runs. When verify cannot run (Nix missing or broken), or `.pi/workflow.json` cannot be read (a merge conflict, say), `/pr` stops with "Verify did not run": nothing is committed, pushed or offered. Fix it, then run `/pr` again. Nothing is committed, pushed or opened without the person's explicit confirmation. `/pr` drops attribution lines (co-author trailers, "Generated with …") from the PR text; product names that are the subject of the work stay.

## 8. PR review in CI

Out of package, but setup prepares it. The same `verify` commands, agentlint included, must run in the project's CI. What passes locally must pass in CI with the same list. If they diverge, setup or the retro fixes it.

## 9. Deploy

Out of package. The project pipeline deploys once the PR is approved.

## 10. Manual verification

Out of package, on purpose. A person has the last word on functionality in the deployed environment. `verify-app` and `.pi/evidence/` make that check short and targeted. They do not replace it.

## Self-compaction

The `self-compact` extension (`src/self-compact/`) tracks context use and lets the agent ask for a compaction with a handoff note.

- **The tool.** Calling `self_compact` ends the agent's turn. Once the run is over, pi compacts with the note, then sends a message that resumes the agent. Escape drops the compaction, with no resume. `/compact` and `/self-compact-now` never resume.
- **Thresholds.** Notice, warning and force (`--compact-notice`, `--compact-warning`, `--compact-force`: token counts or percentages, default 75%, 85%, 90%), and `--compact-buffer` for tokens kept free below the model limit (a token count such as `32k`, default 0). The notice and warning messages go to the model only and are not shown in the chat. At the force threshold the next tool call is blocked, and a visible message tells the model to call `self_compact` with a note; if it does not, its next calls end the run, and pi compacts and resumes without a note. When the agent's final answer crosses the threshold, pi compacts after the run and does not resume.
- **Status.** Pi's own footer stays. From the notice threshold on, a status entry reads `context 77% (notice) · compacts at 90%` (the tier is notice or warning). Below it, nothing is added. `/self-compact-info` shows the thresholds in tokens and the current use.
- **Failures.** When a compaction fails, pi shows the error and resumes the agent with it. After two failures in a row, compaction is off (forced or scheduled, and `self_compact` answers that it is not compacting); the status entry and `/self-compact-info` read `compaction off after 2 failures (run /compact to retry)`. A compaction that succeeds, such as `/compact`, turns it back on. After a failed forced compaction, or one that leaves use at the force threshold, it does not force again until use drops below it.
- **Summary rules.** By default the summary keeps the latest request word for word and what failed, and drops tool output the work already used. A `prompt` (`--compact-prompt`, or `prompt` in the config) replaces these rules. `/self-compact-now [note]` compacts with these rules plus your note; `/compact [instructions]` is pi's own and does not use them. If a compaction is already running, `/self-compact-now` says so and does nothing.
- **Config.** The `selfCompact` key of `pi-improved.json` and of `.pi/workflow.json`: `{ default: { notice?, warning?, force?, buffer?, prompt? }, models: { "provider/model": {...} } }`. Each file's profile for the model is resolved first, then the project's values win. The old `self-compact.json` files are moved into these keys once at startup.
- **Misconfiguration.** Enforcement is skipped, with a one-time error, when the thresholds are misordered, the buffer is not smaller than the context window, or force is at or above the context window minus the buffer.

## Internals

**State.** `.pi/workflow.json` is project state (versioned; keys in the [README table](../README.md#config)). `.pi/task.json` is the active task (local, in `.gitignore` with `.pi/metrics/` and `.pi/evidence/`): `id`, `title`, `ticket`, `status` (`planning` | `implementing` | `done`), `plan`, `spec`, `planChecks`, `progressOff`, `allowedExtra`, `baseCommit`, `understanding` (`asked` once the check is sent), `startedAt`, `completedAt`. The model's write and edit tools cannot change either file. The setup offer's "Don't ask again" is kept per user in `<agent dir>/pi-improved-state.json` (a list of project paths), not in `.pi/workflow.json`.

**Config.** Every option can sit in the user's `<agent dir>/pi-improved.json` (`~/.pi/agent`, or `PI_CODING_AGENT_DIR`) and in the project's `.pi/workflow.json`; the project wins. Plain objects merge key by key, arrays and scalars are replaced, and the state keys (`setup`, `verify`, `connectors`...) are read from the project only; `language` is the one setup answer the global file may hold, as a default. `updateManifest` writes the project file alone, so `/setup` and `/skills` never copy global values into the repo, except `language`, which `/setup` records in the project; `/models` writes the global file unless the phase is set in the project or you run `/models project`. The numbers this document quotes (questions, rules, retries, plan size, retro cadence) are the `limits` keys in the README table; a bad `limits` value falls back to the global one, then to its default, and `/doctor` says so. `/doctor` checks the type and range of each preference in both files (not `language`) and names unknown project keys. `computer`, `subagentPanes` and `selfCompact` used to live in `computer.json`, pi's `settings.json` and `self-compact.json`: `legacy-config.ts` copies each into the new file once at startup (only where the key is missing) and notifies. The global `computer.json` and `self-compact.json` are then renamed to `<name>.migrated` (`.migrated.2` and so on when that name is taken); a project's `.pi/self-compact.json` and pi's `settings.json` are left alone, and the notice asks you to delete the file or remove the key. After that only the new files are read.

**Cost controls.** Verify runs are recorded per task with a kind: progress (runs and failures) and gate (runs, failures, premise lines). `/cost` shows the active task's phase, cost and tokens per phase, and the last risk level; with no active task it shows the latest finished tasks, like `/metrics`. `/metrics` covers the last 10 finished tasks. In its review column, `skipped (low risk)` means skipped as low risk, `skipped` means the review did not run (it failed or was cancelled) and `n/a` means not requested (`review.minLevel`); `approved (discarded)` is a verdict that was not used. The line `Reviews skipped as low risk: N (estimated $X saved)` shows the estimate only when at least one review cost money. `maxReport` is in the README table. Running `/setup` again on a finished setup warns about the strong-model cost and asks before repeating; the startup offer never fires then.

**Models per phase.** `/models` sets `setup`, `implement`, `review` and `escalate` as `provider/model`, in the global file by default (`/models project` for this project only). A missing `setup` or `implement` uses the session model; a missing `review` means no diff review (the plan check then uses the setup model); a missing `escalate` uses `review`, then `setup`. The strong model runs once in setup, in the plan check, in the diff review when risky, and on the escalated fix attempt (the 3rd by default). Everything else uses the cheap model.

**Skills per phase.** Skills live in `vendor/skills/` and each role gets only the ones it uses (`/skills` changes them; a missing skill is ignored). `/skills` first asks which phase to change. Back returns to the phase list, and Done saves and prints the result once. Esc at any point leaves without saving. The implement skills are injected once the plan is recorded; the others are in the phase prompt; on-demand skills may be read when the work needs them. The model never picks an injected skill.

| Role | Injected | On demand |
|---|---|---|
| setup | grilling, domain-modeling, pstack-technical-writing, writing-for-agents, pstack-create-verification-skill | research |
| plan | tdd, contract-first | how, architect, codebase-design |
| implement | principles-implement (tdd and contract-first arrive with the recorded plan) | handoff |
| diagnose | diagnosing-bugs, principles-diagnose | why, benchmark-checklist, principle-explain-the-number |
| review (read-only subagent) | code-review, pstack-blast-radius, principles-review | none |
| learn | retro, correct | pstack-maintain-verification-skill |
| plan check (subagent) | a short brief (naming rule and five checks), no skills | none |

`interrogate` (a short adversarial pass: every finding needs a command and its output) and `reflect` are opt-in only. The main session also gets a base prompt: the `unslop` skill (when bundled) and two working-style lines. Subagents never get it. `basePrompt: false` in `.pi/workflow.json` turns it off.

**Gates.** All blocking happens in code, on pi events: `agent_before_settle` (contract, verify, review, close), `tool_result` (write count, MCP text as ticket evidence) and `tool_call` (files outside the plan, dependencies, migrations, interactive agentlint commands, and write or edit calls on `.pi/workflow.json` or `.pi/task.json`). `setup_finish` and `task_plan` are always declared, so the tool list never changes and the prompt cache survives phase changes; outside their phase they return an error. The model asks the person through the `ask_user` tool (options plus "Other", or an open question answered in their own words); without a UI it tells the agent to choose and say so.

**Subagents.** Children launch via pi-subagent in tmux, read-only (`read,grep,find,ls` plus `codemode`, whose scripts reach only those four: the `mcp__none` entry keeps MCP tools out), with a brief file and a time limit. Inside a child (`PI_SUBAGENT_RUN_DIR`) the extension registers nothing: no setup offers, blocks or questions nobody can see. Their cost goes to the task telemetry. Above the editor, one line per child of the session (such as `⠋ review · read · 2 turns · …`), plan check and review included: state, current tool, turns, tool calls, model, context tokens and time. A child leaves it 5 minutes after it finishes; `/subagent` still lists it. When pi runs inside tmux (`$TMUX` and `$TMUX_PANE` set), each child gets a pane beside pi (`tmux split-window -d`, so focus stays on pi) attached to its tmux session while it works, so you can watch it or type to steer it; the pane closes when the child goes idle or stops. In Tern, Stencil's terminal, the same happens only if `"subagentPanes": "tern"` is in the global file `pi-improved.json` and `TERN_PANE` is set; it is not detected on its own. `/subagent` picks a child and focuses its pane, or opens one that stays until the child stops; outside tmux and Tern it attaches like pi-subagent's and there is only the widget. Both replace pi-subagent's own widget and `/subagent`, unless pi-subagent is installed in pi itself.

**Pictures.** The `show` tool draws a picture in the chat through the terminal's image protocol (Kitty or iTerm2: Tern, Kitty, Ghostty, WezTerm, iTerm2; not inside tmux). Elsewhere, with pi's `terminal.showImages` off, and in `pi -p`, the picture is saved and the model is told the user saw only its path ("Saved at <path>"); in RPC mode the client gets the file and the model is told it was sent, not that it was seen. It takes a PNG, JPEG, GIF or WebP file as is, and renders an SVG file, an HTML file or HTML/SVG markup (mockups, styled tables) with the headless Chromium from Nix (chrome-headless-shell, no system browser needed): the page is measured, then saved as a PNG at twice its size in `~/.pi/agent/renders/`. The model gets only the path, so a picture costs no image tokens. For charts the tool description tells it to plot to a PNG first (matplotlib or similar); for diagrams, to write a ```` ```mermaid ```` block, which pi itself draws as text (flowchart, sequence, class, state, ER).

**Portability.** `pi install git:github.com/OnishellT/pi-improved` is enough; a local path (`pi -e <clone>`) needs `npm install` in the clone, again after every pull, because pi installs nothing for it. pi-subagent and agentlint are bundled (the bundled agentlint is only the fallback: a project that enforces rules keeps its own devDependency). System requirements that cannot be packaged: Node >= 22.19 and Nix. Nix is mandatory: tmux, git, gh, bash and the headless Chromium (`show` on HTML and SVG, the isolated browser) come from one nixpkgs pinned by `flake.lock`, which `src/nix.ts` reads, so there is a single pin. Each is built or fetched on first use with `nix build --out-link <agent dir>/nix-roots/<nixpkgs rev>/<attr> --print-out-paths` (the link is a GC root, one folder per pin, so a garbage collection cannot delete a path a session uses; delete `nix-roots/` to free them), cached for the process, and its `bin` is put first on the PATH of the command that needs it only (`env PATH=…`; verify keeps the inherited PATH after the Nix dirs). Missing Nix is reported with the install command for the OS from nixos.org/download. `/doctor` prefetches and reports each package. Out of scope: `tern`, Node, the desktop, the browser in relay mode, and ssh (the system's: Nix openssh rejects macOS `UseKeychain`). git over https needs one login, gh's: if the helper configured for github.com is not one Nix git can run (it finds only its own cache/store/netrc by name; macOS `osxkeychain` is in Apple git's system gitconfig, which it never reads), the call gets `-c credential.https://github.com.helper=!<gh>/bin/gh auth git-credential`, never written to disk because store paths change after a GC. `flake.nix` also offers pi itself (`nix profile install github:OnishellT/pi-improved`) on the same pin.
